Focused roadmap · post-v0 alternative

Put the first pixels on screen

A deliberately narrow graphics milestone: render a deterministic kernel-owned image through QEMU, then prove the same drawing code on Raspberry Pi 4. No desktop, terminal, input stack, or userspace graphics API yet.

01

Define “graphics” as one honest vertical slice

The goal is not a graphical operating system. It is proof that the kernel can acquire a display surface, draw into memory safely, and make those pixels visible on both supported platforms.

In scope

Deterministic scene

Clear the screen, draw colored rectangles and lines, then render a short label with a tiny fixed bitmap font.

In scope

Two display backends

QEMU virtio-gpu first; Raspberry Pi firmware mailbox second. Both expose the same framebuffer description.

Explicitly later

No interaction layer

No keyboard, mouse, terminal emulator, compositor, windows, acceleration, or user-process access.

Release invariant: graphics failure must never hide boot diagnostics. Initialize UART first, report each graphics stage over serial, and continue to a clear GRAPHICS:FAILED outcome when a display is unavailable.

02

Share pixels, isolate hardware protocols

The portable boundary is a linear framebuffer plus an explicit present operation. Device discovery, allocation, negotiation, and cache rules stay in platform code.

Boot sceneFixed colors, geometry, and “THEKORN OS” label
Software rendererBounds-checked pixel, fill, line, and glyph primitives
FramebufferAddress, width, height, pitch, byte length, XRGB8888
Display backendvirtio-gpu flush or Pi mailbox scanout

Portable code owns what pixels mean. Platform code owns how a visible scanout is acquired and when written pixels become visible.

Kernel contract

Framebuffer carries a byte slice, dimensions, pitch, and format. Rendering uses pitch rather than assuming tightly packed rows and clips every primitive to the surface.

Platform contract

initDisplay returns a surface or a typed failure. present publishes a dirty rectangle; the Pi implementation may be a cache barrier/no-op while virtio-gpu submits transfer and flush commands.

03

Choose the route with the fewest false shortcuts

These choices optimize for a useful kernel mechanism, deterministic testing, and eventual board parity—not for the fastest possible colored pixel at any cost.

Choose

virtio-gpu-device on the QEMU MMIO transport

It matches the project’s existing virtio-mmio discovery and queue work, is available in the pinned QEMU, and exercises a real paravirtual display protocol. Start in polling mode with one control queue.

Reject for now

ramfb as the main backend

It can produce pixels quickly, but requires a second fw_cfg protocol and offers less reuse with the existing virtio transport. Keep it only as a fallback if virtio-gpu scope proves disproportionate.

Choose

One fixed format and a preferred 800 × 600 mode

Use XRGB8888 internally. Accept a different negotiated Pi pitch or size, but do not introduce generic pixel conversion until a second format is actually required.

Choose

Kernel-owned, single-buffered rendering

Allocate whole pages from the physical-frame allocator and identity-map them for DMA. A second buffer, damage tracking, and user mappings are follow-on work driven by tearing or performance evidence.

Defer

Graphical console mirroring

Do not couple the first display gate to scrolling, control characters, panic reentrancy, or concurrent writes. A framebuffer console should be its own later milestone.

04

Build in seven reviewable gates

Every gate leaves serial boot intact and has a narrow exit condition. Land portable rendering before either hardware backend so most behavior is host-testable.

Implementation state: G0–G1 are complete. The display contract and opt-in QEMU profile are followed by an allocation-free renderer with validated pitch arithmetic, clipped pixel/rectangle/line/glyph primitives, a fixed 8 × 8 label font, and an exact complete-scene hash. G2 is active. Physical-hardware verification gates are deferred by project decision and will be recorded separately rather than blocking software implementation.

06

Keep ownership visible in the file layout

Names are provisional, but the boundaries should not be: portable pixels in the kernel, device protocols under their platform, and only genuinely shared virtio mechanics extracted.

src/kernel/framebuffer.zig

Surface description, pixel format, checked offset calculation, and renderer primitives.

src/kernel/boot_scene.zig

The deterministic first image and fixed bitmap glyph data.

src/platform/qemu_virt/virtio.zig

Shared MMIO transport and split-queue mechanics extracted only when G2 begins.

src/platform/qemu_virt/virtio_gpu.zig

GPU commands, responses, resource lifecycle, scanout, transfer, and flush.

src/platform/rpi4/mailbox.zig

Mailbox status protocol and aligned property request/response transport.

src/platform/rpi4/framebuffer.zig

Framebuffer property tags, bus-address conversion, and presentation visibility.

scripts/smoke-virt-graphics.sh

QMP screenshot capture, serial marker checks, timeout handling, and image assertions.

build.zig

Opt-in run/smoke profiles that attach virtio-gpu-device without changing headless gates.

07

Retire the risky assumptions early

The hardest parts are device ownership and visibility, not drawing rectangles. Sequence the plan so each uncertainty fails before graphical-console scope can obscure it.

08

Stop when pixels are trustworthy

This checkpoint is complete when graphical output is a dependable kernel facility—not when it resembles a desktop.

  • The same scene renderer runs unmodified on QEMU and Pi 4.
  • QEMU uses virtio-gpu 2D through virtio-mmio and validates every response.
  • Pi 4 acquires and validates a 32-bit HDMI framebuffer through the mailbox.
  • Rows honor returned pitch and all drawing is clipped and overflow-checked.
  • An automated QEMU screenshot gate proves visible output.
  • A physical Pi serial transcript and display capture prove board parity.
  • Display absence produces a serial failure marker rather than a hang.
  • All existing serial, storage, MMU, scheduler, and process gates still pass.
  • No graphics API is exposed to EL0 in this checkpoint.
  • README documents run, verification, and physical-board workflows.

Natural next choice: after this gate, choose either a framebuffer text console (if observability is the priority) or a read-only userspace framebuffer demo (if process/device boundaries are the learning goal). Do not silently bundle either into first pixels.
